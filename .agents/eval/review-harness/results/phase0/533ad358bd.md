# Hostile review — domain-delete FK race + log-viewer visibility

## The question that comes first

The diff does what it claims for the two headline bugs:

- **FK race on delete**: `_delete_domain_chunk_locked` (`backend/services/domain_deletion.py:133`) takes `SELECT ... ORDER BY id FOR UPDATE` on the domain rows before nulling/deleting. Verified against PostgreSQL's own docs (the "Caution" note under the Locking Clause in `sql-select.html`) that `ORDER BY` is evaluated *before* the row lock is taken on each row at `READ COMMITTED` — i.e. `.order_by(Domain.id).with_for_update()` really does acquire locks in ascending-id order, so two concurrent deleters (bulk task vs. daily cleanup) can't deadlock each other. `FOR UPDATE` also genuinely conflicts with the `FOR KEY SHARE` a child `INSERT` takes on its parent row, so this does close the original "commit-then-delete" race from the reported traceback.
- **Log viewer blindness**: the `<N>` syslog-priority stdout prefix (gated on `$JOURNAL_STREAM`, which systemd sets — confirmed against systemd docs) plus the writable-dir fallback plausibly fix "Errors Only is always empty" and "file logging silently disabled." The message-level level-parsing fallback in `api/logs.py` is reasonable defense-in-depth on top.
- Binding requirements S0–S3, S6, S7 are all present: `cleanup_expired_domains` now calls `clear_and_delete_domains` (S0), every DB-exception branch calls `db.rollback()` before retry/continue (S1), lock order is deterministic (S2), `WatchedFileHandler` replaces `RotatingFileHandler` (S3), `set_local_lock_timeout` exists (S6), and the single-delete `IndexError` from `deleted[0][1]` on an empty list is gone, replaced with a 409 (S7).

That said, the retry/partial-failure machinery introduced to "handle the race" and be "engineered to be scalable" has a real defect in how it interacts with Celery's own timeout contract, and the new tests don't touch the actual DB behavior the fix depends on.

## Findings, most important first

1. **`backend/services/domain_deletion.py:211`** — `except Exception as exc:` in `clear_and_delete_domains` swallows Celery's `SoftTimeLimitExceeded` and treats it as an ordinary chunk failure instead of letting it abort the task.
   `SoftTimeLimitExceeded` subclasses `Exception` (see the fallback `SoftTimeLimitExceeded = RuntimeError` in `backend/database.py:15`), so it lands in this handler. `_is_retryable` (line 79) returns `False` for it (not an `IntegrityError`/`OperationalError`, no PG sqlstate), so it's classified as a permanent per-chunk failure via `_failure_reason` and the outer `for start in range(0, total, batch_size):` loop (line 195) simply moves on to the next chunk — it does not stop the run.
   This breaks the graceful-stop contract this same codebase already establishes elsewhere: `backend/database.py:114` (`except (SoftTimeLimitExceeded, KeyboardInterrupt, asyncio.CancelledError) as exc: ... raise`) and `backend/workers/dns_health_worker.py:1049` / `:1190` (`except SoftTimeLimitExceeded: ... break`, explicitly to "finalize with partial results... before the hard kill"). `cleanup_expired_domains` (`time_limit=600, soft_time_limit=580`) and `bulk_dns_operation`'s delete branch (`time_limit=7200, soft_time_limit=7100`) both call into `clear_and_delete_domains`/`delete_domains_in_batches`, so a soft-limit hit mid-delete now gets absorbed as "chunk failed," and the loop keeps grinding through remaining chunks (each with up to 3 retries and a 120s statement timeout) until the *hard* `time_limit` SIGKILLs the worker with no graceful finalization — the exact failure mode the soft/hard limit pair and the `dns_health_worker.py` pattern exist to avoid. Old code had no try/except around the delete loop at all, so this is a regression introduced by this diff. Fix: add `except (SoftTimeLimitExceeded, asyncio.CancelledError):` above the broad `except Exception`, re-raise, matching the pattern already used twice in this codebase.

2. **`tests/test_domain_deletion_retry.py`** (whole file, e.g. `_patch` at line 77) — every test monkeypatches `_null_send_log_domain_refs` and `_delete_domain_chunk_locked` out entirely and drives orchestration with a `_FakeSession`. That's a fine test of the retry/partial-failure bookkeeping, but none of it exercises the claim the fix rests on: that `SELECT ... ORDER BY id FOR UPDATE` really blocks a concurrent `INSERT` via the `FOR KEY SHARE` conflict, that lock order is what prevents deadlock between two real transactions, or that `lock_timeout` actually produces `55P03` under contention. This is exactly the kind of Postgres-specific behavior that's easy to get subtly wrong (verifying the ORDER BY/lock-order claim required checking Postgres's own docs, not the code comment) and it shipped with zero integration coverage against a real Postgres instance. For a fix whose entire point is "safe under concurrent sends," a test that opens two connections and reproduces the original race (or at minimum asserts the lock is held across the small-table + delete statements) is missing.

3. **`backend/services/domain_deletion.py:142-151`** — the fix closes the race on the *delete* side by making a concurrent send's `INSERT INTO send_logs` block on `FOR KEY SHARE` and then, once our transaction commits the domain deletion, fail that insert with a fresh `ForeignKeyViolationError` on its own statement. That's a legitimate trade (better a rejected insert than a broken delete), but this diff doesn't touch the sending code path and nothing here shows it tolerates that new failure mode (retry, drop-and-log, or surface to the operator). Before this ships, confirm the send path that inserts `send_logs` rows catches `IntegrityError`/`ForeignKeyViolationError` gracefully — otherwise the original bug ("deleting domains: task failed") has been traded for a new one ("sending randomly fails when a domain is being deleted") that's harder to notice because it's scattered across every in-flight send instead of concentrated in one delete call.

4. **`backend/services/domain_deletion.py:198-224`** — retries within a chunk (`DOMAIN_DELETE_MAX_ATTEMPTS = 3`) have no backoff/jitter; on `continue` (line 224) the next attempt starts immediately. For the contention sqlstates about *waiting* (`55P03 lock_not_available`, `40001 serialization_failure`) rather than instantaneous conflict (`40P01 deadlock_detected`), retrying with zero delay against a still-busy row just re-creates the same contention. Low severity on its own (bounded by `lock_timeout`/`statement_timeout` either way), but worth a cheap fix given the task explicitly asks for this to be "engineered to be scalable."

## Note on dispositions

Findings 1 and 3 are the ones worth blocking on: #1 is a concrete, evidenced regression against this codebase's own established pattern (proven by two other call sites in the same repo); #3 is a scope question (does the send path already handle this, or does it need to?) that only someone with visibility into the sending code can close out. #2 and #4 are real but lower-stakes — coverage and a minor retry-storm nit, respectively.
