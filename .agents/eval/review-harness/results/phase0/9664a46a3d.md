Reviewed the diff (`src/app/dashboard/connect/page.tsx`, +80/-16 lines) against `REVIEW-INTENT.md`, the file's existing conventions, `src/app/globals.css`, and `src/lib/supabase.ts`. This repo (`web/`) is frontend-only — the backend endpoint the intent doc cites (`src/auth/auth.controller.ts:64`) lives in a separate `/server` repo not present in this tree, so its claims (idempotency, actual Google revocation, Vault deletion) cannot be independently reproduced from here; this review is scoped to what the frontend diff does and whether it correctly reflects that contract, not to the backend itself.

**Does the code do what it's supposed to do?** Mostly. The confirm-gate correctly blocks connect/reconnect while armed, correctly hides "Disconnect" once already disconnected (idempotency guard on the client side), clears the banner at the right transitions, and the copy accurately mirrors the backend's stated scope (audits/tools kept). One defect breaks the stated safety intent outright — see #1.

1. `src/app/dashboard/connect/page.tsx:203` — `className="btn btn--danger"`, but `.btn--danger` is never defined anywhere in the codebase (`grep -rn "btn--danger"` matches only this one usage; `src/app/globals.css:117-158` defines `.btn`, `.btn--ghost`, `.btn--block` — no danger variant). The class silently falls through to plain `.btn`, so "Confirm disconnect" renders identically to a primary/positive action (pine-green background), not as a destructive action. This directly contradicts the plan's own stated rationale for adding the confirm step at all ("a mis-click costs a full Workspace-admin re-consent, so I'm guarding it") and its claim to use "existing button styles" — `btn--danger` isn't existing, it's a new, undefined one. Fix: add a `.btn--danger` rule to `globals.css` next to `.btn--ghost` (e.g. `--btn-bg: var(--red); --btn-fg: var(--paper);`, reusing the `--red` token already defined at `globals.css:29` and used for the suspended/error state in `src/constants/status.ts:10`).

2. `src/app/dashboard/connect/page.tsx:191-238` — the DOM swap from `Disconnect` → `Cancel`/`Confirm disconnect` (and back) unmounts/remounts buttons with no focus management. A keyboard user who activates "Disconnect" loses focus to `<body>` and must tab from the top of the page to reach "Cancel" or "Confirm disconnect" for a destructive, hard-to-undo action (full Workspace-admin re-consent to undo). Same on reverse transition after Cancel/success/error. Fix: move focus to the new primary control (e.g. `ref` + `.focus()` on "Cancel" when entering confirm mode, and back onto "Disconnect" when leaving it).

3. `src/app/dashboard/connect/page.tsx:180-189` — the footnote text/color change that announces "This revokes access at Google. Audits and tool data are kept." on entering confirm mode has no `aria-live` region. A screen-reader user who triggers "Disconnect" via keyboard gets no announcement that the action state — and the meaning of the now-relabeled buttons — changed. Fix: wrap the footnote `<p>` in `aria-live="polite"`, or add `role="status"` to the button-group container.

4. `src/app/dashboard/connect/page.tsx:103-104` — on success, status is set optimistically (`setStatus('disconnected'); setConnectedAt(null)`) from the 200 response alone, rather than re-running `loadStatus()` to confirm the RLS-scoped row actually reflects `disconnected`. Low severity (the endpoint's claimed contract makes this safe today), but it diverges from `loadStatus`'s existing role as the single source of truth for connection state and would mask a backend/DB write that silently failed after returning 200. Fix: call `void loadStatus()` in place of the two manual setters, matching how the rest of the component treats Supabase as ground truth.
