# ms-domain-delete-fk-race · soft-gate · replicate 1 · 127k tokens

## Hostile Review — domain-delete FK race + log-viewer visibility

Scope: `backend/api/domains.py`, `backend/api/logs.py`, `backend/database.py`, `backend/logging_config.py`, `backend/services/domain_deletion.py`, `backend/workers/{bulk_dns_worker,cleanup_worker}.py`, `scripts/deploy.sh`, plus new/updated tests.

**Correctness of the core fix (verified):** `_delete_domain_chunk_locked` (`backend/services/domain_deletion.py:133-168`) takes `SELECT ... FOR UPDATE` on the domain rows before nulling residual `send_logs` refs and deleting. Postgres FK-RI triggers take a `FOR KEY SHARE` lock on the parent row for every child INSERT, which correctly conflicts with the held `FOR UPDATE` — this genuinely closes the "commit-then-delete" race the ticket reported. Lock order is globally ascending (`sorted(set(domain_ids))` in `clear_and_delete_domains`, `sorted(chunk_ids)` per chunk) so the bulk-delete path and the daily `cleanup_expired_domains` path can't deadlock each other. All six binding requirements (S0 cleanup routed through the locked delete, S1 mandatory rollback, S2 deterministic lock order, S3 `WatchedFileHandler`, S6 lock-timeout helper, S7 partial-failure accounting / no `IndexError`) are present and match their stated intent. The journald `<N>`-prefix + message-text-fallback double mechanism for level recovery is sound and not redundant (the prefix fixes raw `journalctl -p err`; the text fallback also recovers levels from log lines written before this deploy).

1. **The fix relocates the race to concurrent senders, and nothing here confirms they tolerate it — `backend/services/domain_deletion.py:142-151`, `backend/services/campaign_engine.py:802`.**
   Holding `FOR UPDATE` on a domain row blocks any concurrent `send_logs` INSERT referencing it. Once the delete transaction commits, that blocked INSERT resumes — but the domain row is now gone, so the INSERT itself throws `ForeignKeyViolationError`/`IntegrityError`. `campaign_engine.py`'s retry wrapper (`run_campaign`, line ~802) only catches `asyncpg.exceptions.DeadlockDetectedError` for its exponential-backoff retry — not FK violations. So a domain deleted while `run_campaign` is mid-insert can now raise an *unhandled* `IntegrityError` up through campaign execution, aborting that run — a failure mode that did not previously exist on the send side (the old, buggy code let sends always succeed and only the delete failed). The task explicitly asked to "handle the race" end-to-end; this diff only proves the delete side, and doesn't test or confirm the send side degrades gracefully. Fix: either wrap the `SendLog` insert/commit paths to catch and gracefully skip/log a domain-not-found FK violation, or explicitly verify (with a test or a traced code path) that this is already tolerated before calling the race "handled."

2. **Raw exception text is returned to API clients — `backend/services/domain_deletion.py:100-106`, `backend/api/domains.py:3376,3402-3404`.**
   `_failure_reason`'s fallback branch (`return f"{type(exc).__name__}: {str(exc)[:160]}"`) fires for any exception that isn't a classified `IntegrityError`/`OperationalError`/known SQLSTATE. That string flows straight into the single-delete `HTTPException.detail` (line 3376) and the bulk-delete response's `failed_domains[].reason` (line 3402-3404), and separately into `progress.increment(..., error=f"{domain_name}: {reason}")` in `bulk_dns_worker.py`, which an authenticated user can read via the progress-polling endpoint. `str(exc)` on a SQLAlchemy `DBAPIError` typically embeds the failing SQL and bound parameters. This is exactly the "secrets or environment-specific values" / information-disclosure class the review axis calls out. Fix: never surface `str(exc)` to a client-facing field; keep the curated messages for the known cases and use a generic "unexpected error, see server logs" for the fallback — `exc_info=True` is already logged server-side, so nothing is lost.

3. **`except Exception` in the retry loop can silently downgrade a real bug into a "domain still referenced" failure — `backend/services/domain_deletion.py:211-233`.**
   `_is_retryable`/`_failure_reason` only recognize `IntegrityError`/`OperationalError` and specific SQLSTATEs, but the surrounding `except Exception as exc` catches everything — a stray `AttributeError`/`NameError` from a future edit to `_delete_domain_chunk_locked` would be swallowed, logged, and reported to the caller identically to "database contention," rather than propagating and failing loudly. It is logged with `exc_info=True`, which is a real mitigation, but the API/monitoring surface can no longer distinguish "expected DB contention" from "the code is broken." Project doctrine explicitly flags suppression of this kind. Fix: narrow the except clause to `(IntegrityError, OperationalError)` (which is everything `_is_retryable`/`_failure_reason` actually understand) and let anything else propagate.

4. **Stale function name in test failure messages — `tests/test_domain_deletion_fk_cleanup.py:55,62`.**
   Both assertion messages still say `"...not cleared by clear_domain_references..."` / `"clear_domain_references nulls FK(s)..."`, but that function was removed by this diff (replaced by `_delete_domain_chunk_locked` / `clear_and_delete_domains`); the file's own module docstring was updated to drop the name but these two strings weren't. Anyone who trips this guard in the future gets pointed at a symbol that no longer exists. Violates the project's own "docs describe the code as it is now" rule. Fix: update both messages to name `_SMALL_TABLE_DOMAIN_FKS`/the current helper.

5. **Duplicated, drifting log-dir/logrotate provisioning — `scripts/deploy.sh:222-921` vs `scripts/setup-logging.sh:8-19,42-58`.**
   `deploy.sh` now creates `/var/log/email-system` and (only if absent) `/etc/logrotate.d/email-system` with one policy. `setup-logging.sh` independently creates the same directory and *unconditionally* overwrites the same logrotate file with a slightly different policy (`create 0644 $APP_USER $APP_USER` line present there, absent in deploy.sh's version). Two sources of truth for the same config, and running `setup-logging.sh` after `deploy.sh` silently reverts logrotate to the older policy. Not a functional bug today, but a real drift risk. Recommend filing to the debt log or folding `setup-logging.sh`'s log-dir/logrotate steps out in favor of `deploy.sh`, keeping only the unique journald-limits step.

6. **Bulk-delete response order silently changed — `backend/api/domains.py:3390-3405`.**
   The old code queried `.order_by(Domain.name)` and returned `deleted_names` alphabetically. The new path returns `succeeded` built from `sorted(set(domain_ids))` (UUID order), so `domains: [...]` in the bulk-delete response is no longer name-sorted. Minor, but worth confirming no frontend consumer relies on that ordering before shipping.

7. **No backoff between retry attempts — `backend/services/domain_deletion.py:198-233`.** Three immediate retries with no jitter beyond the 10s `lock_timeout` wait itself; under the sustained heavy-contention scenario that prompted this fix, clustered immediate retries could still fail together. Low priority — the lock_timeout already imposes real spacing — but worth a note if contention proves worse than expected in prod.
