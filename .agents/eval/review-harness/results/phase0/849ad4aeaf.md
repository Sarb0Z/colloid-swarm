## Hostile Review — Disconnect button (`src/app/dashboard/connect/page.tsx`)

1. **`page.tsx:203` — `.btn--danger` class does not exist; the confirm-disconnect button renders as the primary/positive CTA, not a warning.**
   `className="btn btn--danger"` is the only place `btn--danger` appears anywhere in the tree (confirmed via `grep -rn "btn--danger"` across the whole repo — it's in the diff and nowhere else). `src/app/globals.css` defines exactly three button variants: `.btn` (base, `--btn-bg: var(--pine)` — the app's brand green, same hue as the "Connected" status pill), `.btn--ghost`, and `.btn--block`. There is no `.btn--danger` rule, so the class is a no-op and "Confirm disconnect" falls back to plain `.btn` — visually identical to "Connect Google Workspace" / "Reconnect". This directly contradicts the implementer's own stated design rationale: "a mis-click costs a full Workspace-admin re-consent, so I'm guarding it, but with the existing button styles" — except no existing danger style exists to reuse, so the guard is cosmetic only. The one piece of red they did add (the footnote text at line 184, `var(--red)`) is easy to miss since it sits to the *left* of the button row while the button itself — the actual click target — reads as a normal affirmative action. Fix: add a `.btn--danger` rule to `globals.css` using the existing `--red` / `--red-wash` tokens (already defined at globals.css:29-30 and used elsewhere, e.g. `status.ts:10`), or ship the confirm button as `btn--ghost` styled red to reuse what genuinely already exists.

2. **`page.tsx:190-238` — arming the confirm step moves focus off-screen for keyboard users.**
   The button row is a full conditional swap (`confirmingDisconnect ? <Cancel/Confirm> : <Disconnect/Connect>`), not a visibility toggle. A keyboard user who activates the "Disconnect" button causes that element to unmount; React does not move focus to either new "Cancel" or "Confirm disconnect" button, so focus reverts to `<body>`. The user must re-tab from the top of the page to reach the control that now controls an irreversible, re-consent-costing action — and the same happens in reverse on "Cancel". No `aria-live` region announces the state change either, so screen-reader users get no signal that the button they just activated turned into a confirmation step. Fix: after setting `confirmingDisconnect(true)`/`false`, programmatically focus the new primary control (ref + `.focus()` in a `useEffect` keyed on `confirmingDisconnect`), or keep both button pairs mounted and toggle `hidden`/`tabIndex` instead of conditional unmount.

3. **`page.tsx:59-118` — `connect()` and `disconnect()` duplicate the same auth-boilerplate shape.**
   Both functions independently do: `supabase.auth.getSession()` → throw "session expired" if missing → build a `Bearer` header → `fetch` → throw a generic error on `!res.ok`. That's now two verbatim copies of ~10 lines of non-business-logic boilerplate. Per the repo's own DRY-after-YAGNI rule, two call sites is the point where this stops being speculative — a small `authorizedFetch(path, init)` helper would remove the duplication and centralize the "session expired" edge case in one place. Not blocking; worth a follow-up rather than re-review.

4. **`page.tsx:101` — a single generic error string collapses distinguishable server responses.**
   The endpoint is documented as bearer-guarded and throttled 10/min per IP (per REVIEW-INTENT.md), but `disconnect()` treats every non-2xx the same: "Could not disconnect Google Workspace. Please try again." A 429 (rate-limited) and a 401 (token expired server-side, distinct from the client-side "no session" case already special-cased above) both tell the user to just retry, which is actively wrong advice for a 429. Low priority — mirrors the pre-existing `connect()` pattern verbatim rather than introducing a new failure mode, and the two-click confirm flow makes the rate limit hard to hit through this UI in practice.

**Note on scope:** this repo tree is frontend-only — no `auth.controller.ts` is present to independently verify the backend revoke/delete/idempotency claims in REVIEW-INTENT.md. Those claims (Vault deletion, Google-side revoke, row flip, audits/tools untouched) are asserted by the implementer as "verified firsthand" but are unreproducible from this diff; flagging as unverified rather than confirmed or refuted.
