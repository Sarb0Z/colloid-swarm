# ms-domain-delete-fk-race · live · replicate 2 · 142k tokens

## Hostile Review — domain-delete FK race + log-viewer visibility

**Verdict on the core question:** the FK-violation fix is architecturally sound — `SELECT ... FOR UPDATE` on the domain row genuinely conflicts with the `FOR KEY SHARE` lock Postgres's RI trigger takes on an INSERT into a referencing table (send_logs or any of the small tables), so holding it does close the "commit-then-delete" race described in the incident. The stated S0/S1/S2/S3/S6/S7 requirements are each implemented as claimed. But the implementation has a real new bug in exception handling, and the fix's central locking claim is never actually exercised by a test.

1. **`backend/services/domain_deletion.py:211`** — `except Exception as exc:` inside `clear_and_delete_domains`'s retry loop swallows `celery.exceptions.SoftTimeLimitExceeded`. When a chunk's delete raises it, `_is_retryable` returns `False` (it's neither `IntegrityError` nor `OperationalError`), so it's recorded as a permanent per-chunk failure via `_failure_reason`'s fallback branch, and **the loop continues to the next chunk** instead of propagating. This defeats celery's cooperative-cancellation contract: `cleanup_expired_domains` (`soft_time_limit=580`) and `bulk_dns_operation` (`soft_time_limit=7100`, `backend/workers/bulk_dns_worker.py:862`) both call into this loop. On a large batch nearing the soft limit, the worker keeps grinding through remaining chunks (each burning up to `DOMAIN_DELETE_MAX_ATTEMPTS(3) × lock_timeout(10s)` = 30s) until celery's *hard* `time_limit` kills the process — instead of exiting cleanly with the partial result already gathered. This codebase already has an established pattern for exactly this: `backend/database.py:114` (`run_worker_async`) and `backend/workers/dns_health_worker.py:1049,1190` explicitly catch and re-raise/handle `SoftTimeLimitExceeded` separately. This new loop doesn't follow it. **Fix:** re-raise `SoftTimeLimitExceeded`/`asyncio.CancelledError`/`KeyboardInterrupt` before the generic `except Exception`.

2. **`backend/services/domain_deletion.py:94-100`** (`_failure_reason`) — every `IntegrityError`/SQLSTATE 23503 is collapsed into the single canned string `"still referenced by active sends after retries"`, discarding the actual failing constraint/table. This exact codebase has hit "a new domain FK isn't in the cleanup set" *twice already* (`warmup_inboxes`, `campaign_sequence_contacts.chosen_domain_id` — see the comment at line 25-32 and `tests/test_domain_deletion_fk_cleanup.py`). If it happens a third time and the guard test isn't run before deploy, production will permanently fail every delete for that table yet always report "active sends," actively misdirecting whoever investigates — the opposite of the "fix error handling and propagation" the user asked for. **Fix:** include the DBAPI error detail (constraint/table name, or at minimum `str(exc)[:160]`) in the 23503 branch too, not just the generic fallback.

3. **`tests/test_domain_deletion_retry.py`** — the load-bearing correctness claim of this whole fix (that `SELECT ... FOR UPDATE` on the domain row blocks a concurrent send's `FOR KEY SHARE`, closing the race) is never exercised. Every test in this file monkeypatches away both `_null_send_log_domain_refs` and `_delete_domain_chunk_locked`, so only the retry/rollback *orchestration* is verified — not the actual Postgres locking behavior that is the entire point of the change. For a fix addressing a production data-loss/crash incident, nothing here independently reproduces the claim with two real concurrent transactions (one holding the domain lock, one attempting a `send_logs` insert).

4. **`backend/services/campaign_engine.py:748`, `backend/services/warmup_engine.py:1815`** — a send that loses the lock race to a concurrent delete now gets an FK violation on **its own** `send_logs` insert (previously the delete crashed instead, or the send silently won). That's the architecturally correct outcome, but it's a new failure surface this diff introduces into the send path, and nothing in this diff confirms `run_campaign`'s per-contact send loop degrades gracefully (skip/log/retry) rather than aborting the whole campaign run when `db.add(log)` fails at flush.

5. **`backend/workers/cleanup_worker.py:236`** (`soft_time_limit=580`) — worst-case blocking per 10-domain chunk is now up to 30s (3 attempts × 10s lock_timeout) under heavy contention. With ~20+ chunks (200+ simultaneously-contended expired domains), cumulative waiting alone can approach/exceed the soft limit before steps 4-6 (mail_forwarding cleanup, Redis budget keys, expiry alerts) run for that cycle. Combined with finding #1, this would silently truncate a day's cleanup run rather than fail loud. Worth sizing against actual expected daily-expiry volume, since the user explicitly asked for this to be "engineered to be scalable."

6. **`scripts/deploy.sh:230-241`** vs **`scripts/setup-logging.sh:47-58`** — both write `/etc/logrotate.d/email-system`, but the deploy.sh copy lacks the `create 0644 $APP_USER $APP_USER` line the setup-logging.sh copy has. Since deploy.sh only writes the file `if [ ! -f ... ]`, whichever script runs first on a box wins permanently and the two configs silently diverge. Not currently consequential (`copytruncate` doesn't need `create`), but it's two sources of truth for the same file — consolidate to one.

**Not flagged, checked and found sound:** UUID `sorted()` gives a real total order (closes the deadlock-ordering requirement S2); `WatchedFileHandler` + external logrotate is correct for multi-process file logging vs. the old `RotatingFileHandler` corruption risk; `$JOURNAL_STREAM`/`SyslogLevelPrefix` prefix mechanism checks out against the actual systemd unit files (no `SyslogLevelPrefix=no` override, `StandardOutput` defaults to journal); the `not_found` bulk-delete count bug (double-counting duplicate ids) is fixed correctly via `set()`; the single-delete endpoint's `IndexError` (S7) is fixed; `_dir_is_writable` fallback path (`/opt/email-system/logs`) is writable by the same user that owns the deploy checkout, consistent with how `deploy.sh` runs.
